# 美团销售智能助手需求规格（v2）

| 属性 | 内容 |
| --- | --- |
| 状态 | 设计中 |
| 版本 | v2.0 |
| 目标版本 | 生产级 MVP |
| 后端语言 | Python 3.12 |
| 部署形态 | 多实例（本地 docker-compose / 生产 Kubernetes） |
| 技术基线 | MySQL 8 + Milvus 2.5 + Kafka + Redis；LangGraph 编排；env 单层配置 |
| 关联决策 | [ADR 目录](../adr/README.md) |

## 1. 背景

销售人员需要在一次连续对话中完成：销售知识与产品知识问答、销售话术推荐、拜访及业务数据查询、商家信息分析、沟通意图分析和拜访规划。系统既要回答非结构化知识问题，也要安全调用结构化业务数据，并在多轮对话中保持上下文、人格边界和答案可追溯性。

方案采用 Agentic RAG（而非 Naive RAG），并建立可持续的知识回流闭环。Prompt 规则只是防幻觉的一层，最终依靠检索证据门禁、引用校验、权限过滤、反思重试和拒答机制共同保证可靠性。

本规格是全新设计（v2），技术栈相对早期方案调整为 **MySQL（事务 + LangGraph Checkpoint + Outbox）、Milvus（向量 + 原生 BM25 双路召回）、Kafka（异步事件）、Redis（租约 + SSE + 缓存 + 限流）**，配置统一收敛到环境变量层。详见 ADR-0001 至 ADR-0006。

## 2. 目标

1. 提供统一的对话 API，按问题类型路由至专业 Worker Agent，支持 SSE 流式回复与断线恢复。
2. 建立 Parent-Child Chunking、元数据增强、Milvus 向量与 BM25 双路召回、RRF 融合与 Cross-Encoder 重排链路。
3. 对复杂问题动态生成有依赖关系的 Sub-Question，并按需执行 HyDE 和有限反思。
4. 支持短期上下文、异步摘要和长期记忆，且可在多实例服务间一致访问。
5. 通过受控 Tool 查询拜访、商家和销售指标，禁止模型直接访问生产数据库。
6. 建立"对话日志 → 命中知识 → 经验提炼 → 语义审核 → 高价值知识回流"闭环。
7. 达到可观测、可评测、可灰度、可审计、可水平扩容的生产标准，并可在本机一键起全栈开发调试。

## 3. 非目标

1. 不替代 CRM、商家管理系统或数据仓库。
2. MVP 不允许 Agent 自动执行写操作（修改商家资料、创建订单、提交拜访结果）。
3. 沟通意图分析不进行医学、心理疾病或人格诊断。
4. 不保存或展示模型隐藏思维链，只保存结构化决策、工具调用和证据轨迹。
5. MVP 不提供开放式代码执行、任意 SQL 或任意 URL 请求能力。
6. MVP 不做运行时动态配置热更新与按租户在线灰度（配置走 env，见 ADR-0005）。

## 4. 基线假设

| 编号 | 假设 |
| --- | --- |
| A-01 | 服务分为无状态 API、Agent Runtime 和异步 Worker，均可多实例水平扩容。 |
| A-02 | LLM、Embedding、Cross-Encoder 均通过可插拔 Model Gateway 接入，协议兼容 OpenAI API；本地直连公司/外部网关。 |
| A-03 | MySQL 保存事务数据、LangGraph Checkpoint、Outbox 与审计；Milvus 承载向量与 BM25 索引；Kafka 承载异步事件；Redis 保存缓存、租约与 SSE 短期事件；对象存储保存原文。 |
| A-04 | 商家、拜访、销售指标通过只读内部 API 接入；本地开发使用 Mock Adapter。 |
| A-05 | MVP 是完整纵向切片，覆盖知识问答、路由、记忆、业务 Tool、回流、评测和部署。 |
| A-06 | 系统为多租户系统，所有资源均绑定 tenant_id，并在检索前执行 ACL 过滤。 |
| A-07 | 配置统一由环境变量载入，进程启动时冻结，变更经滚动发布生效。 |

## 5. 用户与权限

| 角色 | 主要能力 |
| --- | --- |
| 销售人员 | 发起对话、查询授权知识与业务数据、获得话术和拜访建议、提交反馈。 |
| 销售主管 | 具备销售能力，并可查看授权团队范围内的聚合分析。 |
| 知识运营 | 上传文档、维护元数据和权限、审核回流知识、发布或下线知识版本。 |
| 系统管理员 | 配置模型、Prompt、路由、限流、租户和审计策略，不默认拥有业务数据读取权。 |

权限模型采用 RBAC + ABAC：角色决定能力，租户、组织、区域、商家归属、文档密级和数据范围决定具体资源访问权。

## 6. MVP 范围

### 6.1 P0 能力

- 销售知识和产品知识检索问答，答案带文档、章节、版本等引用。
- 销售话术推荐，结合商家特征、沟通阶段和历史上下文输出。
- 拜访记录、拜访统计、销售指标的只读查询。
- 商家信息汇总、机会点、风险点和下一步行动分析。
- 沟通意图、异议、关注点、情绪倾向和成交阶段分析。
- 拜访规划，包括目标、议程、问题清单、材料和跟进行动。
- Supervisor-Worker 路由、复杂任务规划、记忆治理和知识回流。
- 管理端文档接入 API、离线评测命令和生产可观测指标。

### 6.2 P1 能力

- 主管级团队洞察和批量商家分析。
- 用户可编辑的长期记忆。
- 多模型成本路由和自动降级优化。
- 主动推荐、定时拜访提醒和经人工确认的写操作。

## 7. 功能需求

### FR-001 会话与上下文

1. 系统必须创建、查询、归档会话，并支持 SSE 流式回复。
2. 每条写请求必须支持 `Idempotency-Key`，重复请求不得重复生成消息或重复调用业务 Tool。
3. 同一会话的并发写入必须串行化，并通过版本号防止旧结果覆盖新上下文。
4. 任意实例必须能继续处理已有会话，不依赖粘性 Session 或本地内存。
5. 客户端断线后必须能使用事件游标（Redis Stream + `Last-Event-ID`）恢复尚未过期的流式事件。

### FR-002 问题理解与动态规划

1. 系统必须识别问题领域、复杂度、数据时效性、所需权限和推荐 Worker。
2. 简单问题必须走快速路径，禁止无条件拆解和反思增加延迟。
3. 复杂问题由 Planner 输出类型化执行 DAG，包含 Sub-Question、依赖、目标数据源、预算和完成条件。
4. Sub-Question 默认不超过 4 个，反思重试默认不超过 1 次（均由 env 配置上限）。
5. Planner 输出必须经过 Schema 校验；非法计划回退到单 Worker 安全路径。

### FR-003 Agentic RAG

1. 系统必须将会话问题改写为独立检索问题，同时保留原问题供答案生成使用。
2. 系统必须并行执行 Milvus 语义向量召回与 BM25 关键词召回（Milvus 原生稀疏检索）。
3. 对抽象、短查询、低首轮召回或概念性问题，系统可以生成 HyDE 假设文档扩展检索；HyDE 内容不得作为最终证据。
4. 系统必须使用加权 RRF 粗排、父块扩展、去重和 Cross-Encoder 重排。
5. 系统必须计算证据充分度；证据不足时仅允许有限补检，最终仍不足则明确拒答或请求澄清。
6. 答案中的事实性结论必须能映射至用户有权访问的证据引用。

### FR-004 企业文档处理

1. 系统必须支持 PDF、DOCX、PPTX、HTML、Markdown 和纯文本；扫描件通过可选 OCR 处理（P1）。
2. 文档必须按 tenant、知识库、版本、语言、产品、区域、时效、密级和 ACL 管理。
3. 切分必须保留标题层级、表格、列表、页码和段落位置。
4. 默认使用 Parent-Child Chunking：父块用于答案上下文，子块用于高精度召回；子块间保留可配置 Overlap。
5. 文档发布必须版本化。新版本索引成功前旧版本继续服务；切换必须原子化（Milvus alias）并可回滚。
6. 删除文档必须产生可审计的索引清理任务，并满足数据删除时限。

### FR-005 Supervisor-Worker Multi-Agent

系统至少包含以下 Worker：

| Worker | 职责 |
| --- | --- |
| Knowledge QA | 销售知识、产品知识和制度问答。 |
| Sales Coach | 话术、异议处理和沟通建议。 |
| Business Data | 拜访与销售指标查询。 |
| Merchant Analyst | 商家画像、机会、风险和行动建议。 |
| Intent Analyst | 沟通意图、关注点、异议和阶段分析。 |
| Visit Planner | 拜访目标、材料、议程和后续行动规划。 |

1. Supervisor 必须优先使用确定性规则处理高置信路由，再使用模型补充分流。
2. 每个 Worker 必须拥有独立 System Prompt、工具白名单、上下文视图和输出 Schema。
3. Intent Analyst 可使用"虚拟心理分析师"的观察方法，但只能输出销售沟通信号及证据，不得输出临床判断。
4. Worker 每次调用必须从固定人格模板重新构造上下文，禁止继承其他 Worker 的人格指令。
5. Supervisor 必须以中立统一口吻合成最终答案，并保留各结论的来源和置信度。

### FR-006 业务数据 Tool

1. 所有 Tool 必须通过注册中心声明输入 Schema、输出 Schema、权限、超时、重试和数据敏感级别。
2. Tool 调用前必须完成参数校验和用户数据范围校验。
3. Tool 返回结果必须进行字段裁剪、敏感信息脱敏、大小限制和时效标注。
4. 业务数据和知识文档冲突时，必须展示来源时间并优先采用被定义为权威且更新的数据源。
5. Tool 超时或不可用时必须局部降级，禁止编造查询结果。

### FR-007 两层记忆治理

1. 短期记忆由最近消息、当前任务状态和滚动摘要组成，并受 Token Budget 约束。
2. 达到消息数或 Token 阈值后，系统必须异步生成带版本的滚动摘要（Kafka 触发），不阻塞当前主请求。
3. 长期记忆只保存稳定、可复用且允许保存的信息（偏好、关键实体、已确认目标、高价值经验）。
4. 长期记忆写入前必须经过提取、去重、冲突检测、敏感性检测和置信度门禁。
5. 用户必须能够禁用长期记忆；租户必须能够配置保留期限和删除策略。
6. 长摘要必须支持分层压缩，且保留来源消息 ID，避免摘要逐轮失真无法追溯。

### FR-008 知识沉淀与回流

1. 系统必须关联保存对话、Agent 运行轨迹、命中知识、引用、用户反馈和结果指标。
2. 候选经验提炼必须异步执行（Kafka），并删除无关个人敏感信息。
3. LLM-as-a-Judge 必须按相关性、正确性、可复用性、新颖性、风险和证据支持度输出结构化评分。
4. 语义 Checker 必须检查候选知识与现有知识的重复、矛盾、时效和权限。
5. 高价值候选只进入待审核区，不得由模型直接发布到生产知识库。
6. 审核、发布、撤销和版本切换必须全程审计，并可追溯到原始对话和证据。

### FR-009 反馈与评测

1. 用户可以提交赞踩、问题分类、引用错误和补充说明。
2. 系统必须支持固定 Golden Set 的离线检索评测、生成评测和端到端回归。
3. Prompt、模型、Embedding、切分和排序参数变更必须关联实验版本。
4. 灰度与快速回滚在 MVP 通过部署维度（滚动发布 / Canary）实现（配置走 env，见 ADR-0005）。

### FR-010 运营管理

1. 知识运营可创建知识库、上传文档、查看处理状态、发布版本和下线文档。
2. 管理员可通过重新部署调整模型路由、Prompt 版本、检索参数、预算和熔断策略（env 配置）。
3. 高风险操作必须采用双人复核或审批流，至少包括生产知识批量删除和权限扩大。

## 8. 非功能需求

### 8.1 服务等级目标

| 指标 | MVP 目标 |
| --- | --- |
| API 月可用性 | >= 99.9% |
| 简单问答首 Token 延迟 | P95 <= 3 秒 |
| Agentic 问答首 Token 延迟 | P95 <= 5 秒 |
| 简单问答完整响应 | P95 <= 12 秒 |
| 复杂多 Agent 响应 | P95 <= 25 秒 |
| 检索与重排链路 | P95 <= 1.2 秒 |
| API 错误率（排除调用方 4xx） | < 0.5% |
| 流式断线事件恢复窗口 | >= 10 分钟 |
| 单租户数据删除完成时间 | <= 24 小时 |

延迟目标以模型服务满足约定容量为前提；外部依赖耗时必须单独计量。

### 8.2 容量基线

- 初始支持 50 QPS 持续请求、200 QPS 峰值请求和 1,000 个并发 SSE 连接。
- API、Agent Runtime、Ingestion Worker 和 Evaluation Worker 可独立水平扩容。
- 单租户和单用户均配置并发、Token、Tool 和检索限额，避免资源争抢。
- 所有组件不得依赖单实例内存中的会话状态（会话/Run 状态在 MySQL，短期事件在 Redis）。

### 8.3 安全与合规

- 使用 OIDC/OAuth2 鉴权，服务间使用短期凭证或 mTLS。
- MySQL 行级租户约束和应用层双重校验；Milvus 在召回前应用标量 ACL 过滤。
- 传输和存储加密，密钥由 KMS/Secret Manager 管理，Secret 不进入代码、镜像或日志。
- 日志默认脱敏，不记录完整 Prompt、证件、电话、Cookie、Token 和高敏 Tool 返回值。
- 对文档 Prompt Injection、越权 Tool 调用、数据外泄和资源耗尽建立专项防护。
- 管理操作、数据访问、模型调用、工具调用和知识发布保留审计日志。

### 8.4 工程质量

- 核心领域逻辑单元测试覆盖率 >= 85%，全仓行覆盖率 >= 75%。
- CI 必须执行 Ruff、类型检查、Pytest、迁移检查、依赖漏洞扫描和镜像扫描。
- 关键路径必须具备集成测试、契约测试、故障注入测试和负载测试。
- 数据库变更遵循 expand/migrate/contract，支持滚动升级期间新旧版本并存。
- 本机可用一条命令起全栈（MySQL/Redis/Milvus/Kafka/对象存储），单元测试不依赖外部服务。

## 9. 质量与效果验收

在不少于 500 条、覆盖六类 Worker 和权限场景的 Golden Set 上验收：

| 指标 | 目标 |
| --- | --- |
| Intent/Worker 路由准确率 | >= 95% |
| Retrieval Recall@20 | >= 90% |
| Retrieval NDCG@10 | >= 0.80 |
| Citation Precision | >= 95% |
| Groundedness | >= 95% |
| 权限过滤正确率 | 100% |
| 业务 Tool 参数正确率 | >= 99% |
| 证据不足时正确拒答率 | >= 90% |
| 高价值知识回流误发布数 | 0 |

LLM-as-a-Judge 不能单独作为上线结论。至少 10% 样本由业务专家盲审，并校准 Judge 与人工评分的一致性。

## 10. 端到端验收场景

1. 销售询问产品政策，系统返回准确答案、引用章节和生效日期。
2. 销售结合某商家最近拜访记录请求下一次拜访建议，系统完成权限校验、Tool 查询、知识检索和综合规划。
3. 用户提出跨产品对比问题，Planner 拆分 Sub-Question，并在证据不足时补检一次。
4. 长对话跨实例继续请求，回答保持上下文一致且没有 Worker 人格串扰。
5. 无权访问某区域商家时，检索、Tool、缓存和日志均不泄露相关信息。
6. 模型、Milvus 或业务 Tool 部分故障时，系统按策略降级并明确说明不可用能力。
7. 高质量对话生成知识候选，经 Judge、Checker 和人工审核后发布新版本，并可撤销。

## 11. 发布边界

满足以下条件后 MVP 才允许进入生产灰度：

- P0 功能和端到端场景全部通过。
- 安全、权限、数据删除、审计和灾备检查通过。
- Golden Set 指标达到门槛且无 P0/P1 未解决缺陷。
- 完成容量压测、故障演练、回滚演练和 Runbook 评审。
- 业务、知识运营、安全和研发负责人共同签署发布结论。

## 12. 评审时必须确认

1. 实际部署环境、MySQL/Milvus/Kafka/Redis/对象存储的容量与 HA 约束。
2. 可用 LLM、Embedding、Rerank 模型及其数据合规边界。
3. 商家、拜访、销售指标 API 契约和字段级权限模型。
4. 租户定义、组织层级、文档密级和数据保留期限。
5. 目标 QPS、并发量、SLO、预算和业务峰值。
6. Golden Set 的来源、业务专家和最终验收负责人。
7. Intent Analyst 可使用的对话数据范围及法务/隐私要求。
